# HA rustfs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run a four-pod, erasure-coded rustfs in namespace `rustfs` that serves S3 at `https://s3.k8s.somemissing.info` and keeps reading and writing with any one node down.

**Architecture:** ArgoCD Application `rustfs` installs upstream chart `rustfs` 1.0.6 in distributed mode (4 pods × 1 zvol, `EC:2`). The chart's `extraManifests` carry everything else that lives in the namespace: the client-facing `s3` Service, a cert-manager private CA and two certificates (rustfs picks one by SNI), a metrics collector that Prometheus scrapes, and two NetworkPolicies. Alert rules and their unit tests sit at the repo root like the other rule files.

**Tech Stack:** Kubernetes 1.37, ArgoCD (root app applies repo-root manifests; `application.*.yaml` are child apps), Helm chart `rustfs` 1.0.6 from `https://charts.rustfs.com`, cert-manager 1.21, democratic-csi iSCSI zvols, mittwald secret-generator, kube-prometheus-stack (`release: prom`), `otel/opentelemetry-collector-contrib` 0.165.0, promtool, rclone.

**Spec:** `docs/superpowers/specs/2026-11-25-ha-rustfs-design.md`. Read it first. This plan argues from it and does not repeat its reasoning.

## Global Constraints

- Chart `rustfs` version `1.0.6`, release name `rustfs`, namespace `rustfs`. Leave `image.rustfs.tag` unset.
- Topology: `replicaCount: 4`, `drivesPerNode: 1`, `RUSTFS_STORAGE_CLASS_STANDARD=EC:2`. Do not change these after the first sync.
- Storage: StorageClass `zfs-generic-iscsi-csi`, `250Gi` per PVC, PVC annotation `democratic-csi.org/config` with `homelab:sanoid-skip: "true"` and `syncoid:sync: "false"`.
- Endpoint for every client: `https://s3.k8s.somemissing.info`, path-style, region `us-east-1`. Service `s3` maps 443 → 9000 and 9001 → 9001.
- Root credentials: Secret `rustfs-root`, keys `RUSTFS_ACCESS_KEY` and `RUSTFS_SECRET_KEY`. Never print them. Read them into environment variables with command substitution only.
- TLS directory: one projected volume `rustfs-tls` at `/etc/rustfs-tls`, `RUSTFS_TLS_PATH=/etc/rustfs-tls`. Never mount a second Secret into a subdirectory of another volume.
- Public certificate issuer: ClusterIssuer `cert-manager-webhook-dnsimple-production`. Peer certificate issuer: namespaced Issuer `rustfs-peer-ca`.
- Metrics: rustfs pushes to `http://rustfs-metrics.rustfs.svc.cluster.local:4318`; Prometheus scrapes the collector on 8889. `enableOTLPReceiver` on `prom-kp-prometheus` stays `false`. Do not edit `application.kube-prometheus.yaml`.
- Pods labelled `app.kubernetes.io/name: rustfs` are rustfs server pods only. The collector uses `app: rustfs-metrics`.
- Every rustfs series selector in a rule carries `namespace="rustfs"` (HA) or `namespace="woodpecker"` (CI cache).
- `woodpecker/rustfs.woodpecker.yaml` (the CI cache) does not change.
- Git: branch from `main`, stage explicit paths, never `git add -A`. ArgoCD deploys from `main`, so a merge is a deploy. The orchestrator commits; the user merges pull requests.
- Fencing rule for a node that will not return: the VM is off at the hypervisor before anyone applies the out-of-service taint or force-deletes a pod.

## Review Focus

Conditions the spec implies that are most likely to hurt a person using this service. Each one has its test in the task named.

- **A client starts a new transfer while one pod is down.** It must succeed, with matching checksums, on connections that land on each surviving pod. Task 6, Step 2.
- **A node dies without warning during an upload.** Request failures must stop within 2 minutes and the upload must finish on default retries. Task 6, Step 5.
- **rustfs starts before secret-generator has written the root keys.** The container must wait, not start with missing or default credentials. Task 4, Step 2.
- **The CI cache dies while the HA instance is healthy (or the reverse).** Each instance's missing-metrics alert must still fire. Task 1 unit tests.
- **The service fills to its usable capacity.** The capacity alert must fire at 80% of usable space, which is 40% of raw. Task 1 unit tests.

## File Structure

| File | Responsibility |
|---|---|
| `rustfs-ha-alerts.yaml` (create) | PrometheusRule `rustfs-ha`: pod count, write quorum, restarts, offline drive, capacity, missing metrics |
| `rustfs-alerts.yaml` (modify) | CI cache rules gain `namespace="woodpecker"` matchers |
| `.ci/test/prom-rules/rustfs-alerts.test.yaml` (create) | Unit tests for both rule files with series from both namespaces |
| `namespace.rustfs.yaml` (create) | Namespace `rustfs` |
| `rustfs-root-secret.yaml` (create) | Generated root credentials |
| `application.rustfs.yaml` (create) | Chart values and every in-namespace object except the root Secret |
| `README.md` (modify) | Operator notes: endpoint, new bucket and user, failure behaviour, failed-node recovery, CA rotation |

The spec names one alert, `RustfsHAPodsNotReady`, with two severities. This plan splits it into `RustfsHAPodsNotReady` (warning, fewer than 4) and `RustfsHAWriteQuorumLost` (critical, fewer than 3), because one alert name with two `for` durations needs two rules anyway and the second name says what broke.

The spec asks for a per-pod instance id through `extraEnv`. The live CI cache shows rustfs already sets `service.instance.id` to the pod IP (label `exported_instance`), so the plan adds no variable and Task 4, Step 7 checks that the four pods stay distinct.

```yaml
# Alerts for the HA rustfs instance (namespace rustfs, application.rustfs.yaml).
# Every rustfs_* selector carries namespace="rustfs": the CI cache in namespace
# woodpecker exports the same metric names, and rustfs-alerts.yaml scopes its
# rules the other way. Pod liveness and restarts come from kube-state-metrics,
# so they keep working when the rustfs-metrics collector is down. Design:
# docs/superpowers/specs/2026-11-25-ha-rustfs-design.md
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: rustfs-ha
  namespace: monitoring
  labels:
    release: prom
spec:
  groups:
    - name: rustfs-ha
      rules:
        - alert: RustfsHAPodsNotReady
          expr: kube_statefulset_status_replicas_ready{namespace="rustfs", statefulset="rustfs"} < 4
          for: 15m
          labels:
            severity: warning
          annotations:
            summary: HA rustfs has fewer than 4 ready pods
            description: >-
              {{ $value }} of 4 rustfs pods are ready. The service still reads
              and writes on 3, but a second loss stops writes. If a node is
              down for good, follow the failed-node procedure in README.md.
        - alert: RustfsHAWriteQuorumLost
          expr: kube_statefulset_status_replicas_ready{namespace="rustfs", statefulset="rustfs"} < 3
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: HA rustfs has lost write quorum
            description: >-
              {{ $value }} of 4 rustfs pods are ready; writes need 3.
        - alert: RustfsHARestartLooping
          expr: increase(kube_pod_container_status_restarts_total{namespace="rustfs", container="rustfs"}[30m]) > 2
          labels:
            severity: warning
          annotations:
            summary: "HA rustfs pod {{ $labels.pod }} is restarting repeatedly"
        - alert: RustfsHADriveOffline
          expr: max by (namespace) (rustfs_cluster_health_drives_offline_count{namespace="rustfs"}) > 0
          for: 15m
          labels:
            severity: warning
          annotations:
            summary: HA rustfs reports an offline drive
            description: >-
              {{ $value }} of 4 drives are offline according to rustfs itself.
        - alert: RustfsHACapacity
          # Usable used over usable total, both from the same reporting pod.
          # Never divide by rustfs_cluster_capacity_raw_total_bytes: at EC:2
          # that ratio tops out near 0.5 and this alert would never fire.
          expr: >-
            max by (namespace) (
              rustfs_cluster_capacity_used_bytes{namespace="rustfs"}
              /
              rustfs_cluster_capacity_usable_total_bytes{namespace="rustfs"}
            ) > 0.8
          for: 1h
          labels:
            severity: warning
          annotations:
            summary: HA rustfs is over 80% of its usable capacity
            description: >-
              Usable capacity is {{ $value | humanizePercentage }} full. Every
              byte stored costs two on the shared NAS pool; expand all four
              PVCs together or remove data.
        - alert: RustfsHAMetricsMissing
          expr: absent({__name__=~"rustfs_.*", namespace="rustfs"})
          for: 1h
          labels:
            severity: warning
          annotations:
            summary: HA rustfs metrics have been missing for an hour
            description: >-
              No rustfs_* series from namespace rustfs. Check the
              rustfs-metrics collector Deployment, its PodMonitor, and the
              RUSTFS_OBS_* settings; drive and capacity alerts are blind
              until this clears.
```

# are the environment variable names rustfs reads. Kept at the repo root, out

- [ ] **Step 1: Compute the liveness setting**

Let `T = max(T_FIRST, T_RESTART, T_HEAL)` in seconds. The startup allowance is `initialDelaySeconds + (failureThreshold - 1) × periodSeconds`. With `failureThreshold: 3` and `periodSeconds: 5` that is `initialDelaySeconds + 10`. Require an allowance of at least `2 × T`:

```text
initialDelaySeconds = max(30, 2 × T - 10), rounded up to a multiple of 5
```

Example: `T = 40` gives `initialDelaySeconds: 70`, an allowance of 80 seconds.

- [ ] **Step 2: Check resource usage under the tests**

## HA rustfs (S3)

`application.rustfs.yaml` runs a four-pod erasure-coded rustfs in namespace
`rustfs`. Design: `docs/superpowers/specs/2026-11-25-ha-rustfs-design.md`.

- **Endpoint:** `https://s3.k8s.somemissing.info` for every client, inside
  and outside the cluster. Path-style, region `us-east-1`. Console:
  `https://s3.k8s.somemissing.info:9001`.
- **Capacity:** 4 × 250Gi zvols at `EC:2`, about 500Gi usable. Every byte
  stored costs two on the shared `midline` pool. The zvols are thin, so pool
  space is the real limit; `RustfsHACapacity` warns at 80% of usable.
- **Not backed up.** The zvols are excluded from NAS snapshots and
  replication. A consumer that needs a backup copies its bucket elsewhere.
- **Separate from the CI cache.** `woodpecker/rustfs.woodpecker.yaml` is a
  different, single-pod instance. Alert rules tell the two apart by
  `namespace`.

### Adding a consumer

The root keys in Secret `rustfs/rustfs-root` are for administration only. For
each consumer, log in to the console with the root keys, create a bucket,
create a user with its own access key, and attach a policy limited to that
bucket. Store the consumer's keys the way `## Secret management` describes.

### Failure behaviour

| Pods down | GET of an existing object | PUT |
|---|---|---|
| 1 | yes | yes |
| 2 | yes | no |
| 3+ | no | no |

Two pods down is a degraded state, not a dependable read-only mode: list,
delete and multipart calls have their own thresholds.

A drain or kured reboot moves the pod to the spare worker and reattaches its
zvol; the PDB allows the next eviction only after that pod is Ready. A crashed
node is different: its pod stays `Terminating` on the dead node and nothing
replaces it. The service keeps reading and writing on three pods. Clients see
errors for about [crash failure window] after a crash, then recover without
action.

### A node that will not come back

Three pods have write quorum, so do not rush this.

1. **Fence first.** Confirm at the hypervisor that the VM is off, and keep it
   off. A NotReady node may only have lost its network, with rustfs and
   every other pod still writing to their zvols. A closed iSCSI session on the
   NAS is not a fence, and neither is blocking one LUN.
2. `kubectl taint node <node> node.kubernetes.io/out-of-service=nodeshutdown:NoExecute`.
   This deletes the stuck pods on that node and force-detaches all of its
   volumes.
3. Watch the replacement: `kubectl -n rustfs get pods -w`, `kubectl get
   volumeattachment`, and the democratic-csi controller log. In the rehearsal
   this took [taint-to-four-peers time].
4. If the pod still waits on attachment after 10 minutes, read the CSI
   controller log. Delete the old VolumeAttachment by hand only when that log
   shows the detach cannot finish and the VM is still off.
5. Confirm four pods Ready and
   `rustfs_cluster_health_drives_online_count{namespace="rustfs"}` at 4.
6. Remove the taint before powering the VM back on, or after deleting the
   Node object if the VM will not come back.

### TLS

rustfs serves two certificates and picks one by SNI. Clients get the public
certificate for `s3.k8s.somemissing.info`. Peers use a certificate from a CA
that exists only in namespace `rustfs` (Certificate `rustfs-peer-ca`). Both
come from one projected volume, and rustfs reloads renewals without a
restart.

Rotating the private CA is manual and causes a full outage (about
[rotation outage time] in the rehearsal). cert-manager does not reissue
leaves when a CA changes.

```sh
fp() { kubectl -n rustfs get secret "$1" -o jsonpath="{.data.$2}" | base64 -d | openssl x509 -noout -fingerprint -sha256; }
OLD=$(fp rustfs-peer-ca 'tls\.crt')
kubectl -n rustfs delete secret rustfs-peer-ca
kubectl -n rustfs wait certificate/rustfs-peer-ca --for=condition=Ready --timeout=2m
NEW=$(fp rustfs-peer-ca 'tls\.crt'); [ "$OLD" != "$NEW" ] || echo "STOP: CA did not change"
cmctl renew -n rustfs rustfs-peer
kubectl -n rustfs wait certificate/rustfs-peer --for=condition=Ready --timeout=2m
# Verify against the CA Secret, not the leaf Secret's own ca.crt.
kubectl -n rustfs get secret rustfs-peer-ca -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/ca.pem
kubectl -n rustfs get secret rustfs-peer -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl verify -CAfile /tmp/ca.pem /dev/stdin
[ "$(fp rustfs-peer 'ca\.crt')" = "$NEW" ] || echo "STOP: leaf Secret still trusts the old CA"
# All four together: a pod on the new CA and one on the old reject each other.
kubectl -n rustfs delete pod -l app.kubernetes.io/name=rustfs
kubectl -n rustfs rollout status statefulset/rustfs --timeout=10m
```
